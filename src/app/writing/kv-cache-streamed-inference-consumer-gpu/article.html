How Context Length Affects GPU Memory

The KV cache stores information from every prompt and generated token. For Qwen3-14B, it grows from 1.3 GB at 8K tokens to 5.4 GB at 32K tokens.

Oney ErgeOctober 14, 20265 min read

The KV cache

LLMs generate one token at a time. Attention uses information from the earlier tokens, so inference software stores the keys and values it has already computed instead of recomputing them at every step.

A closer look at attention Optional: a worked example of queries, keys, and values

Queries, keys, values, and attention are fundamental pieces of the transformer architecture [1].

In each layer, attention computes three short lists of numbers for every token: a query, a key, and a value. The query of the newest token is compared with the keys of the tokens available to it. A stronger match gives a higher score, which causes more of that token's value to contribute to the output.

Table 1 works through this for the text “the dog ran.” It scores each available token against the newest one, “ran,” converts those scores into weights, and blends the values into one output for “ran.”

For this simplified example, I omit the usual score scaling and the learned projections that produce queries, keys, and values, and show only the part needed to explain the KV cache.

Each score comes from multiplying the query by that token's key, number by number, and adding the results. Softmax then converts the scores into weights that add up to 1. The output is the sum of every token's value multiplied by its weight:

wi=esi∑jesj,output=∑iwivi (1)

where si is the score of token i, wi is its weight, and vi is its value.

Storing keys and values instead of recomputing them

When the model adds a new token, the keys and values of earlier tokens do not change. The KV cache keeps them in GPU memory, while each new token adds one key and value in every decoder layer.

Size of the KV cache

Qwen3-14B uses grouped-query attention: 40 query heads share 8 sets of keys and values [2]. The cache size is

MKV=2×L×nkv×dh×b×T (2)

The factor 2 counts keys and values; L is the number of layers; nkv is the number of key/value sets; dh is the size of each one; b is bytes per value; and T is prompt plus generated tokens.

For Qwen3-14B in BF16, this is

2×40×8×128×2=163,840 bytes

or about 0.16 MB per token: 1.3 GB at 8K tokens, 5.4 GB at 32K, and 21 GB at 128K.

Total memory for Qwen3-14B on an 8 GB laptop GPU

Qwen3-14B needs 29.5 GB for BF16 weights. A 3K-token prompt and answer add about 0.5 GB of KV cache, and my laptop already uses 2.2 GB. That exceeds 32 GB before GPU software and temporary activations.

Even 4-bit weights do not by themselves make the workload fit: the 7.4 GB estimate plus system use leaves no room for the cache, runtime allocations, and format metadata. The calculator below makes those trade-offs visible.

What the cache changes

The KV cache is not a one-time model cost: it grows with every prompt and output token. On a small GPU, it competes directly with the memory available for weights and temporary work.
