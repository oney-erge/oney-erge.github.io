Running large language models on small GPUs · Part 1

Memory requirements of language model inference on a consumer GPU

I run language models on a laptop GPU with 8 GB of memory, a size I think is common for consumer hardware. This series is about what happens when the model I want to run is much larger than that memory, and what can be done about it without changing the released model weights. This first part calculates what has to fit in that memory, and why a 14B model does not.

Oney ErgeSeptember 13, 202612 min read

A language model is, in large part, a collection of numbers called weights that are learned during training. Text is converted into lists of numbers and passed through a series of layers. Each layer transforms the list using its own weights, then hands the result to the next layer.

A GPU is fast at this work because it runs thousands of multiplications at the same time. That speed only helps if the weights arrive as fast as the GPU can use them. The GPU's own memory sits next to its processor on the graphics card and, on my GPU, can be read at about 448 GB/s [5]. Data in the computer's main memory or on disk must first travel over the PCIe connection, which carries at most about 32 GB/s [5], more than 10 times less. Storage is slower still. For this reason, the weights are normally loaded into GPU memory before inference, the process of using a trained model to generate text.

The practical problem is size.

Throughout this series, I use Qwen3-14B, the 14B model of the Qwen3 family that Alibaba's Qwen team released on April 29, 2025 [1]. Its released BF16 weights require about 29.5 GB. My GPU, an NVIDIA RTX 3080 Laptop GPU, has 8 GB of advertised memory.

There are two practical ways to deal with this mismatch. One is to make the weights smaller, normally through quantization. The other is to keep most of the weights outside GPU memory and load them only when they are needed.

This post first calculates what has to fit in GPU memory. It then shows what happens when the second approach is used.

GPU memory during inference

Everything using the GPU competes for the same memory. For this discussion, I divide that memory into five parts:

Msys+Mrt+MW+MKV+Mact≤MGPU (1)
Msys
System and display. Memory used by the operating system, the desktop, connected monitors, and other open programs before the model starts. On my laptop, with Windows, a browser, and a code editor open, nvidia-smi reported 2.2 GB in use.
Mrt
GPU software. Memory held by the NVIDIA driver and by libraries such as PyTorch, outside the model itself. This depends on the software stack; measure it on your own machine with nvidia-smi, the same way as Msys, before and after loading the library.
MW
Weights. Fixed by the model and its number format. Calculated below.
MKV
Stored keys and values. Memory kept for every token of the input prompt and of the generated answer. It grows as the conversation grows. Explained below.
Mact
Activations. Temporary results inside the layer that is being computed, released when the layer finishes.

MGPU is the memory on the graphics card. GPU makers label memory in binary units, so my "8 GB" card holds 8.6 GB in the decimal units this post uses throughout. I still call it an "8 GB GPU" in prose, but every chart and calculation below uses 8.6 GB.

On my laptop, that leaves about 6.4 GB of physical capacity before any model weights, KV cache, runtime allocations, or activations are added.

Only MW and MKV can be calculated directly from the model; the rest of this post works out those two terms, while the other 3 depend on the machine and must be measured separately. Note that the weights alone cannot use the whole GPU. If they did, no memory would remain for the prompt, the answer, or the operating system.

Number formats for weights

The weights are by far the largest fixed term in Eq. (1), so the first question is how much memory one weight requires. The memory needed for the weights follows directly from how many there are and how many bytes each one takes:

MW=N×b (2)

where N is the number of weights and b is the bytes each weight uses.

A model is normally trained and released using one fixed number format for every weight. One way to fit a model into less memory is to store each weight with fewer bits than it was released with. This is called quantization, and it directly lowers b in Eq. (2). Fewer bits give fewer possible values per weight, so quantization discards some information and can reduce accuracy. Table 1 lists the formats used in this series.

Table 1. Common number formats for language model weights. The size under each format is the storage for one weight; 1 byte is 8 bits.

FormatWhat it keepsTypical use
FP324 bytesWide range of values and fine precisionTraditional training and reference calculations
FP162 bytesFine precision, but a smaller range; very large values can overflowInference on GPUs, mixed-precision training
BF162 bytesThe same range as FP32, with less precisionTraining and release of most recent open models
8-bit integer1 byteQuantized: 256 levels per weight plus a scale factor per group; some accuracy lostInference at half the memory of BF16
4-bit integer0.5 byteQuantized: 16 levels per weight plus scale factors; more accuracy lostLocal inference on consumer GPUs

BF16 was designed to keep the range of FP32 in half the memory, and training in BF16 reaches the same results as training in FP32 [2]. It is the released format for Qwen3-14B, and also for other recent open model families such as Llama and Gemma. With N = 14.8 billion weights and b = 2 bytes, Qwen3-14B needs 29.5 GB.

Careful 8-bit quantization keeps accuracy close to the original model [2]. A study of more than 35,000 experiments compared model families at a fixed total memory budget, for example a 60B model in 4-bit against a 30B model in 8-bit. It found 4-bit almost always the better use of that memory. This is why 4-bit versions are popular for local use. For Qwen3-14B, 8-bit weights need 14.8 GB and 4-bit weights need 7.4 GB.

This series keeps BF16. In this series, exact weights means that inference ultimately uses the same BF16 values released with the model, not an 8-bit or 4-bit approximation. Afterimage [6], the engine this series builds toward, is designed to run these exact weights: it does not introduce weight error through lossy quantization. Where this post reports the same output tokens across methods, such as in Table 6, that is a separate, measured result, and not a guarantee that follows automatically from using exact weights.

Parts of a language model

To understand how a model larger than the GPU can still run, we need to know which parts of the model are used in sequence.

Model files and configuration

Downloading Qwen3-14B from Hugging Face gives 3 kinds of files. The weights are stored in several .safetensors files. A tokenizer splits text into tokens and gives each token an ID number. The file config.json describes the shape of the model. Table 2 shows the entries of config.json used in this post.

The number of layers is not a fixed property of language models in general. It is an architecture choice the Qwen team made for each model size when they designed and trained it, and it is fixed once training finishes. The downloaded config.json only records that choice, along with every other structural setting, so that software loading the model knows its exact shape. In the Qwen3 family, the 0.6B model has 28 layers, the 8B model 36, the 14B model 40, and the 32B model 64 [1]. Any model's own values can be read from its own config.json file.

A token enters the model through the embedding table, passes through the decoder layers in order, and leaves through the output head.

Embedding table

The embedding table is the first stop for the input prompt. It takes each token of the prompt and looks up its row in a table, converting that piece of text into a list of numbers. Those numbers are what the decoder layers then work with; the model never touches the original words again after this step. Table 3 shows a simple version with 4 tokens and 3 numbers per row.

Table 3. A simple embedding table. The numbers are illustrative.

Token IDTokenRow of numbers
0the[0.2, −0.1, 0.7]
1dog[0.9, 0.3, −0.4]
2ran[−0.5, 0.8, 0.1]
3in[0.0, −0.6, 0.2]

The text "the dog" splits into the tokens "the" and "dog", and the embedding table replaces each one with its row from Table 3. No arithmetic happens at this step; it is only a lookup.

Decoder layers

Coming out of the embedding table, every token has a list of numbers. Each decoder layer takes these lists and updates them a little, using information from the other tokens in the text, then passes the updated lists to the next layer. Qwen3-14B repeats this 40 times, one decoder layer after another, so that by the last layer, each token's list reflects the whole sentence around it, not just the original word.

Inside each layer, this happens in 2 steps. Attention lets a token pull in information from earlier tokens, explained below with the KV cache, and a feed-forward step then updates each token's list on its own. Both steps use the operation described at the start of this post: multiplying a list of numbers by the layer's own weights. Every layer has its own weights, 330M per layer.

Output head

The output head turns the decoder layers' final numbers back into an actual next word. It holds one row per token in the model's vocabulary, the same list of tokens the embedding table started from. It compares the last token's numbers against every row to give each one a score. With the greedy decoding used in this series, the highest-scoring token is chosen as the next token of the answer. In Qwen3-14B, the output head is the same size as the embedding table, 778M weights.

A note on vocabulary: an unfamiliar word is split into smaller known tokens; the model does not need a separate output row for every possible word.

No single part is large. The embedding table and the output head are the largest, and each decoder layer is smaller than 1 GB. The difficulty is the number of layers: 40 of them need 26.4 GB. Figure 1 draws the weights to scale against the GPU.

This sequential structure is important. The model contains 29.5 GB of weights, but all 29.5 GB do not have to be on the GPU at the same instant.

Memory for the prompt and the answer: the KV cache

LLMs generate text one token at a time: after reading the prompt, they produce the first token of the answer, add it to the text, and repeat. Each new token depends on all the tokens before it. The step that looks back at earlier tokens is called attention.

The next part works through exactly how attention computes those keys and values. If you already know how attention works, skip ahead to "Storing keys and values instead of recomputing them."

A closer look at attention

Queries, keys, values, and attention are fundamental pieces of the transformer architecture used by most modern LLMs [3]. In each layer, attention computes 3 short lists of numbers for every token: a query, a key, and a value. The query of the newest token is compared with the keys of all tokens so far. A good match gives a high score, and a high score lets more of that token's value flow into the newest token's list.

Table 5 works through this for the text "the dog ran." It scores each earlier token against the newest one, "ran", turns those scores into weights, and blends every token's value into one output list for "ran", shown in the table's last row. For this simplified example, I omit the usual score scaling and the learned projections that produce queries, keys, and values, and show only the part needed to explain the KV cache.

Table 5. A simple attention step for the newest token, "ran", whose query is [0, 2]. The numbers are illustrative.

TokenKeyValueScore, query × keyWeightContribution, weight × value
the[1, 0][0.2, 0.1]00.06[0.01, 0.01]
dog[0, 1][0.9, 0.4]20.47[0.42, 0.19]
ran[1, 1][0.5, 0.7]20.47[0.24, 0.33]
Blended output for "ran"[0.67, 0.52]

Each score comes from multiplying the query by that token's key, number by number, and adding the results. A key that points in a similar direction to the query scores higher. A function called softmax then turns the scores into weights that add up to 1, shown in the table above. The newest token's output is the sum of every token's value, scaled by its weight, also shown in the table.

wi=esi∑jesj,output=∑iwivi (3)

where si is the score of token i, wi is its weight, and vi is its value. "The" contributes almost nothing to the blended output, because its key does not match the query.

Storing keys and values instead of recomputing them

When the model adds the next token, "in", the keys and values of the earlier tokens do not change. Without storing them, the model would have to redo that work for every earlier token, again and again, each time it adds a new token. Instead, inference software computes each token's key and value once and keeps them in GPU memory. This store is the KV cache. Each new token only adds one column to it, as Figure 2 shows.

Size of the KV cache

So far, this describes one attention calculation per layer. A real layer runs several of these side by side; each one is called a head, and each head can pick up on a different kind of relationship between tokens. Qwen3-14B uses 40 heads per layer. To save memory, groups of 5 heads share the same keys and values, so there are only 8 distinct sets per layer instead of 40. This sharing is called grouped-query attention [4], and it makes the KV cache 5 times smaller than giving every head its own keys and values. The memory of the KV cache is

MKV=2×L×nkv×dh×b×T (4)

where the factor 2 counts keys and values, and L, nkv, and dh come from Table 2. b is the bytes per number, and T is the number of tokens in the input prompt and the answer together.

For Qwen3-14B in BF16, one token needs 2 × 40 × 8 × 128 × 2 = 163,840 bytes, about 0.16 MB.

An input prompt and answer of 8K tokens together need 1.3 GB. At the model's standard 32K-token context, the KV cache alone needs about 5.4 GB. Its extended context of 128K tokens [1] needs about 21 GB, more than the whole GPU (Figure 3).

Total memory for Qwen3-14B on an 8 GB laptop GPU

Eq. (1) can now be filled in. Qwen3-14B needs about 29.5 GB for its BF16 weights. A short 3K-token input prompt and answer add about 0.5 GB for the KV cache. My laptop's system already occupies about 2.2 GB. That is already more than 32 GB, before GPU software and temporary activations are even counted, far more than the GPU's 8 GB.

A 4-bit version does not fit either: its 7.4 GB of weights plus the 2.2 GB used by the system already exceed the GPU before the prompt is stored. This is why comparing a model file's size directly with the number printed on the GPU box can be misleading. That does not mean a 4-bit Qwen3-14B cannot be run on an 8 GB system with memory-management techniques. It means the weights cannot be treated as the only thing that has to fit. Loading one part of the model at a time

The model still does not fit, but the calculation above suggests another option: the GPU does not need every weight at the same time.

The weights do not all have to be in GPU memory at once. They can stay on disk, and only one part is loaded onto the GPU at a time: load it, use it, then remove it before loading the next part.

Inference happens in two stages. First, the prefill stage processes the whole input prompt at once and builds the initial KV cache. After that, decoding begins: the model generates one token, adds it to the sequence, and repeats. For one generated token during decoding, the order looks like this:

  1. Step 1Load the embedding table's row for the current token, then remove the embedding table from GPU memory.
  2. Step 2Load decoder layer 1, update every token's list with it, then remove that layer from GPU memory.
  3. Step 3Repeat step 2 for each of the other 39 decoder layers, one at a time. Nothing but the layer currently in use ever stays on the GPU.
  4. Step 4Load the output head, score every possible next token, and pick one. Remove the output head from GPU memory.

All of that loading and computing produces exactly one token. To generate the next one, the same sequence runs again, starting from the embedding table.

Because only one part is ever on the GPU at a time, the peak GPU memory in this mode is set by whichever single part is the largest. It is not the sum of all the parts. In Qwen3-14B, that part is the 1.6 GB output head.

Measured streamed execution

Afterimage is an experimental research toolbox for analyzing and optimizing this kind of loading; its minimum-memory setting, measured here, works the same way as AirLLM.

These results solve the capacity problem, but not the performance problem. Both systems run the 29.5 GB BF16 model with measured PyTorch GPU peaks below 2 GB in this configuration. Each generated token then takes about half a minute of request time, including prefill, because the weights are read from disk and moved to the GPU again for every token. The GPU is no longer limited by how many weights it can hold; it is now limited by how quickly the next weights can be prepared and delivered.

AirLLM is faster here because it reads the stored weights directly, with no extra step. Afterimage's minimum-memory setting also has to decode the weights it reads, an extra step covered in a later part of this series.

Loading every layer from storage minimizes GPU memory, but it treats every weight as equally disposable. In practice, some weights may be worth keeping on the GPU, some may be worth keeping in system memory, and others may be cheap enough to reload.

This starts to look like an optimization problem.

Given fixed GPU and system-memory budgets, the question becomes which weights should remain in each memory tier and which should be retrieved again during execution. The best choice may not be determined by weight size alone. It depends on when the weight is needed, how expensive it is to prepare and move, and whether that work delays generation or can overlap with something already running. Later parts of this series will show why that decision cannot be made from tensor size or storage traffic alone.

Conclusions

The GPU memory needed to run Qwen3-14B was calculated from its configuration and compared with my 8 GB laptop GPU. The following were concluded:

  1. GPU memory holds 5 items: system use, GPU software, weights, the KV cache, and activations. On my laptop, the system alone used 2.2 GB before any model was loaded, leaving about 6.4 GB of physical capacity.
  2. The released BF16 weights need 29.5 GB, more than 3 times the GPU memory. Most of this is in 40 decoder layers of 0.66 GB each.
  3. The KV cache stores keys and values for every token of the input prompt and the answer. It needs about 0.16 MB per token and 5.4 GB at the standard 32K context.
  4. The model uses its major weight groups sequentially. Loading each group only when it is needed lowers the measured GPU peak to under 2 GB in the tested AirLLM and Afterimage configurations. That costs about 30 seconds of request time per generated token.

Therefore, keeping the released BF16 weights on this GPU requires most of those weights to live outside GPU memory and be delivered again as execution progresses. That is why one token can take about 30 seconds. The memory problem has become an optimization problem: deciding which weights are worth keeping on the GPU, which are worth keeping in system memory, and which are cheap enough to reload. The next part looks at what happens during those 30 seconds, one step at a time, to see where the time actually goes.
