How Speculative Decoding Speeds Up Inference

A small draft model proposes tokens before the large model verifies them in one pass. On my 8 GB laptop, fixed speculation reduced Qwen3-14B from 17.4 to 9.2 s per generated token at a similar GPU peak.

Oney ErgeOctober 14, 20266 min read

A streamed large model normally needs one full pass for each answer token. On this laptop, that pass takes about 20 s because most weights must be read from storage again.

Speculative decoding lets a smaller draft model guess ahead, then lets the large target model check those guesses in one pass [1]. The target model still chooses every kept token.

Drafting and checking tokens

The target here is Qwen3-14B. The draft is Qwen3-0.6B from the same family [4]; it stays on the GPU and uses about 1.3 GB.

For a fixed draft length k, one round is:

  1. 1The draft model proposes k tokens.
  2. 2The target model checks all k positions in one pass.
  3. 3Matching tokens are kept from the start of the draft. At the first mismatch, the target model's token replaces the draft and the rest is discarded.

Each pass produces between 1 and k + 1 tokens. Table 1 shows a four-token draft where one target pass adds three answer tokens.

Without speculation, those three tokens would need three target-model passes.

The same output as the large model alone

With greedy decoding, every kept token is the target model's own top choice for the same preceding text. The draft changes the number of target-model passes, not the intended output.

With sampling, a draft token cannot simply be compared with one choice. Speculative sampling accepts each draft token with a probability set by the scores of both models and, after a rejection, samples a replacement from a corrected distribution. Leviathan et al. and Chen et al. showed that the result follows the target model's own distribution exactly [1].

Parallel checking can change floating-point operation order, so matching output tokens remains a measured result rather than an assumption.

Tokens per pass and time per token

How many tokens one pass produces depends on how often the draft is right. If the target model accepts each draft token with the same probability, independently of the others, the expected number of tokens per pass is [1]:

E=1−αk+11−α (1)

where α is the acceptance rate, the fraction of draft tokens that the target model accepts, and k is the number of draft tokens per round.

Figure 1 plots Eq. (1) for drafts of 4 and 8 tokens.

Longer drafts pay off only when the draft is usually right. At a 0.5 acceptance rate, 8 tokens add little over 4; at 0.9, they add about 2 tokens per target pass.

The time per generated token follows from the cost of one pass and the cost of drafting:

ttoken≈tpass+ktdraftE (2)

where tpass is the time of one pass of the target model with the draft tokens included, and tdraft is the time the draft model needs for one token.

Here, tpass is about 20 s and tdraft is tens of milliseconds [5]. Drafting is therefore small relative to one slow target pass. When the model fits on the GPU, drafting and verification are a larger fraction of the work.

Fixed speculation measured on my laptop

Afterimage [5] uses fixed speculation: the draft always proposes k = 8 tokens. I tested 4 prompts, 4 generated tokens each, greedy decoding, and a cleared page cache before each run.

The draft left 2.7 GB for the target model. The whole run reached a measured PyTorch peak of 3.8 GB.

Two prompts finished in one pass; the code prompt needed three because the draft disagreed more often.

Across the four prompts, fixed speculation took 9.2 s per generated token at a 3.8 GB peak. Without speculation, the 4 GB Afterimage plan took 17 s at 3.9 GB. Every prompt produced the same output tokens in both runs.

In a later 8-token run, fixed speculation averaged about 4.6 s per token [5]; the longer answer spreads prefill across more tokens.

GPU memory required by the draft model

The draft model occupies about 1.3 GB throughout the run, leaving less space for target-model weights. Together with the target model's minimum, this configuration needs about 3 GB, so it cannot reach AirLLM's 1.6 GB operating point [5].

The gain depends on the prompt, and these answers are short. A fixed policy also proposes 8 tokens even when the draft is going poorly.

Why it helps here

In this streamed workload, a draft token took milliseconds while a target-model pass took about 20 s. Accepted guesses therefore remove expensive target-model passes.

Fixed 8-token drafts measured 9.2 s per generated token at a 3.8 GB peak, against 17 s at 3.9 GB without speculation. Next: the draft source, length, and verification shape change that trade-off.
