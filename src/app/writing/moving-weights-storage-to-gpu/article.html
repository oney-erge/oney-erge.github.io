Running large language models on small GPUs · Part 3

Moving weights from storage to the GPU during streamed inference

In Part 2, loading Qwen3-14B one part at a time ran the 29.5 GB model in under 2 GB of GPU memory, but each generated token took 27 to 33 seconds. This part follows one weight from storage to the GPU to see where that time goes, and when it actually delays the answer.

Oney ErgeOctober 14, 20267 min read

Every generated token passes through every decoder layer, so in streamed execution every token also needs every weight that is not already on the GPU. With nothing kept on the GPU, the whole model makes the trip from storage once per pass.

That trip has up to three steps. Each step uses a different part of the computer, and the parts run at very different speeds.

The path from storage to the GPU

A weight that is not on the GPU starts in one of two places. Storage, here the laptop's SSD, keeps the model files permanently. RAM, the computer's main memory, is faster but smaller, and it is emptied when the computer turns off.

To be used, a weight is read from the SSD into RAM and then copied over the PCIe connection into GPU memory, the only memory the GPU computes from at full speed (Part 1).

The operating system keeps recently read files in unused RAM, called the page cache, so reading the same file again can be much faster. On my laptop, a repeated read of the same file reached 16.6 GB/s, about 7 times the cold read [7]. The measurements in this series clear the page cache before each run, so they start from the cold speed. The page cache returns in Part 4.

Three steps for each weight

Before the GPU can use a weight, the weight is read from the SSD, unpacked if it is stored compressed, and copied to GPU memory. The time until it is ready is roughly

tprep≈Sdiskbdisk+tunpack+SbPCIe (1)

where Sdisk is the number of bytes stored on the SSD, bdisk is the read speed, tunpack is the unpacking time (zero for a weight stored uncompressed), S is the size of the unpacked weight, and bPCIe is the copy speed.

Copy over PCIe at 32 GB/s0.02 s0.9 s

Reading dominates. The copy over PCIe, which is often blamed for slow offloading, is more than 10 times faster than the cold read here.

Reading the whole model once takes about 13 seconds, close to half of the 27 seconds per token that AirLLM measured in Part 2. The measured time also includes processing the input prompt, the computation, and the software work around each step.

Lossless compression: fewer bytes to read, more work to unpack

If reading dominates, reading fewer bytes should help.

Afterimage, the engine this series builds toward, stores the weights compressed without loss [7]. A BF16 number has 1 sign bit, 8 exponent bits, and 7 mantissa bits. Only a few exponent values are common, so Afterimage re-encodes the exponent with a Huffman code, which gives frequent values shorter codes [2], the same idea as DFloat11 [3]. Unpacking restores exactly the released bits.

For Qwen3-14B, this shrinks the stored weights from 29.5 GB to 20.3 GB, 1.45 times smaller. At 2.3 GB/s, that saves about 4 seconds of reading per pass through the model.

The saving is not free. Every compressed weight must be unpacked before use, which adds tunpack to Eq. (1). Compression shortens the time to a ready weight only when

S−Sdiskbdisk>tunpack (2)

that is, when the reading time it saves is longer than the unpacking time it adds.

In my measurements, it was not. At the minimum-memory point, Afterimage with compression alone took 33 seconds per token against AirLLM's 27 (Part 2, Table 2): the reading time it saved was spent on unpacking.

Loading during computation

Reading, unpacking, and copying do not have to stop the GPU. A streaming engine can prefetch: while the GPU computes one layer, the next layer is already on its way. FlexGen organizes its whole schedule around this overlap [4].

If the next layer is ready before the GPU finishes, its loading time is hidden. If it is not, the GPU waits.

Only the waiting delays the answer. Two weights can take the same time to load and still cost very different amounts, depending on whether their loading overlaps with computation. Part 4 returns to this point, because it decides which weights are worth keeping close.

Keeping some weights close

The remaining option is to stop moving some weights at all. With spare GPU memory, some weights can stay there permanently. With spare RAM, others can stay there unpacked and skip the read and unpack steps. Table 2 compares measured operating points on my laptop.

MethodMeasured PyTorch peakRequest time per generated token
AirLLM 3.2.0, one layer at a time [6]1.6 GB27 s
Afterimage, compressed, minimum memory1.7 GB33 s
Afterimage, compressed, 4 GB of weights kept on the GPU3.9 GB17 s
Hugging Face Accelerate, weights on GPU, RAM, and SSD [5]3.8 GB14 s

With about 4 GB, both approaches take 14 to 17 seconds per token instead of 27 to 33. The extra memory is spent on weights that no longer make the trip.

This is also where compression finally helps. With fewer bytes left to read and unpacking done in larger pieces, Afterimage's 4 GB plan runs 1.9 times faster than its own minimum-memory point.

That leaves the question this series has been building to. A few gigabytes of spare memory hold only some of the weights. Afterimage's 4 GB plan chose them with a sensible rule: keep the weights that save the most data movement per byte of memory they occupy.

Part 4 shows why that rule can still keep the wrong weights.

Conclusions

The trip of a streamed weight from storage to the GPU was traced on my laptop and compared with measured operating points. The following were concluded:

  1. Each weight is read from the SSD, unpacked if it is compressed, and copied over PCIe. With a cold page cache, reading at 2.3 GB/s dominates: about 13 seconds per pass through the 29.5 GB model, against under 1 second for the copy.
  2. Lossless compression reduces the stored weights from 29.5 GB to 20.3 GB, but at the minimum-memory point the unpacking it adds outweighed the reading it saves: 33 seconds per token against 27.
  3. Loading that overlaps with computation is hidden. Only loading that is not ready when the GPU needs it delays the answer.
  4. Keeping some weights close, with about 4 GB of GPU memory, cut the time per token to 14 to 17 seconds. This is also where compression starts to pay off.

The open question is which weights should get the spare memory. The next part, Part 4, answers it with the method in my paper, which decides by replaying a recorded request.
