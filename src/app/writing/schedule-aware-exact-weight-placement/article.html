Which weights should stay near the GPU?

H6.5 replays a recorded request to choose where each weight tensor should live: SSD, RAM, or GPU memory. In its main Llama-3.3-70B test, it lowered both peak GPU memory and request time against simpler rules, without changing the weights.

Oney ErgeOctober 14, 20266 min read1 min video

The paper's main experiment runs Llama-3.3-70B, whose BF16 weights need about 141 GB, on an NVIDIA RTX 5090 with 32 GB of memory [1]. The same method also chose a different placement on my laptop; the code and evidence are in Afterimage [2].

The placement decision

Each weight tensor, a named array such as one layer's attention matrix, can be compressed or uncompressed on the SSD, unpacked in RAM, or unpacked in GPU memory. A nearer state needs less preparation each request (Guide 3), but uses limited RAM or GPU memory.

In the main experiment, 5.2 GB of the 8 GB GPU budget may hold weights; the rest stays free for temporary work. The RAM budget is 16 GB. Llama-3.3-70B has 723 tensors with several possible states each, too many placements to test live. H6.5 seeks the one that finishes the request soonest without changing any weight.

Same size, different payoff

The main comparison is the data-movement rule from Guide 3: it fills memory with the tensors that save the most data movement per byte. Similar offloading systems use sizes, bandwidths, or fixed rules [3] [4].

But moved data is not the same as lost time: loading that finishes while the GPU computes is hidden. Only a late load delays the answer. Figure 1 shows the simplest case.

A rule based on bytes cannot tell these two layers apart, because they are the same size. In the real model the difference is just as concrete.

In one recorded request with the data-movement placement, the output head, the 2.1 GB final layer that scores the next token (Guide 1), was stored compressed on the SSD. It was read only after the last decoder layer had finished, which took 1.25 s, and then unpacked, which took another 0.31 s. Nothing was left to compute in the meantime, so the GPU waited 1.56 s (Figure 2).

Keeping the output head on the GPU explains this Llama example. It is not the rule H6.5 applies. H6.5 scores whole placements, and on my laptop it kept the output weights in RAM and rearranged other tensors instead. Whether moving a tensor helps depends on what else is happening when that tensor is needed, and the recording contains all of it.

Replaying a recorded request

H6.5 starts by running one real request and recording every read, unpack, copy, and computation, together with what had to wait for what. This record is a dependency graph: each event starts only after the events it depends on have finished.

To score a candidate placement, H6.5 replaces the preparation times of the tensors it moves with the times measured for their new states, and replays the graph:

cj=dj+maxk∈pred(j)ck,T^=maxjcj (1)

where dj is the duration of event j under the candidate placement, pred(j) are the events it waits for, cj is the time it completes, and T̂ is the predicted finish time of the request.

The search starts from several reasonable placements, including the data-movement rule's, improves them step by step, and keeps the one with the lowest predicted finish time, with a penalty when the prediction varies between recorded requests. For Llama-3.3-70B, it scored 1,817 complete placements in about 3.4 seconds. The whole preparation, mostly recording and measuring, took about 9 minutes, and is repeated only for a new model, machine, workload, or budget. The chosen placement is checked on a recording it was not chosen with, frozen, and then tested on new, live requests.

What the placement changed

With the same budgets, H6.5 placed 198 of the 723 tensors differently from the data-movement rule. It moved 191 tensors from the GPU to the SSD, 82 of them stored uncompressed so that they skip unpacking, and used the freed space mainly for the 2.1 GB output head (Figure 3). Both placements keep almost the same amount of weights on the GPU and in RAM, and are predicted to read about the same 78 GB from the SSD per pass.

The memory result is the most consistent: peak extra GPU memory was lower in every one of the 20 matched Llama requests. Most of the difference is the output head. The data-movement placement must make temporary room of about 2.1 GB to rebuild it at the end of each request, while H6.5 keeps it ready.

The latency gain varied between sessions: about 2% in the first study, within run-to-run variation, and 19% in the second. It reflects the whole placement, not the head alone. Three later repeat studies on new prompts, 35 rounds in all, found about 18% lower request time overall than the data-movement rule and 15% lower than the time-saving rule, with peak extra GPU memory lower in every round.

On my laptop, the method picked a different plan. For Qwen3-14B and Gemma 2 27B it kept the output weights in RAM and rearranged attention and feed-forward weights instead. The procedure is the same; the answer depends on the model, the machine, and the budgets.

Limits

These are results on two machines, with one-token requests as the main workload.

In an exploratory 32-token test with Qwen3-14B, the placement chosen for one-token requests was slower than loading everything from the SSD. The cause was RAM, not the GPU. That placement kept 8 GB of weights in RAM, which left less room for the page cache from Guide 3, and the replay does not model the page cache. With no weights kept in RAM, H6.5 was the fastest method in a follow-up on new prompts.

The replay predicts. Only live measurements, like those in Table 1, count as results.

The point

What belongs in scarce memory depends on when loading it delays the request, not only on its size or byte traffic. H6.5 records one request, replays 1,817 feasible placements in about 3.4 s, then freezes the placement for live requests.

Against the data-movement rule with the same budgets, the chosen Llama placement changed 198 of 723 tensors, used 23% less peak extra GPU memory in all 20 matched requests, and lowered request time 13% overall. Next: use one slow pass to generate several tokens.
